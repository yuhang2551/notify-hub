# 设计说明

**中文** | [English](design_EN.md)

2026-10-27 写的一页设计，2026-10-28 改成纯推送工具（0.3）后重写。哪些做了、哪些还没做，以 [更新记录](../CHANGELOG.md) 为准。

## 它解决什么

邮件监控要推到手机，实验跑完要推，Claude Code 等你确认也想推。每个程序各写一遍 Lark 推送，Lark 凭证就散在好几个地方，卡片的样子、出错时怎么办也各不一样。

notify-hub 把「发到 Lark」这一层抽出来：程序只管说「发生了什么、有多急、谁说的」，notify-hub 负责马上把它变成一张卡片，发到你的手机上。

## 只管发，不管时间

0.2 版的 notify-hub 自己还管着时间：有发件箱、免打扰时段、每日汇总，还有一个每天跑三次的定时任务。邮件监控也有自己的定时任务和汇总。两个程序各有一套时间表：邮件汇总 9 点和 18 点发，notify-hub 的定时任务 8、12、18 点跑，夜里的通知还要在 notify-hub 里再存一道。一条通知几点到，要把两边的设置放在一起才算得出来。

0.3 起分工改成：

| | 负责 |
|---|---|
| notify-hub | 现在就发；连不上当场重试几次；还不行就告诉调用方 |
| 调用方（比如邮件监控） | 什么时候检查、什么时候发、夜里发不发、哪些合成一张汇总、发不出去的怎么办 |

时间规则放在调用方，是因为只有它知道一条通知值不值得半夜叫醒你、能不能等到汇总。推送工具不知道邮件是谁发的，只能按级别一刀切。

0.2 版的发件箱、免打扰和汇总是怎么做的，见 0.2.1 的 [设计说明](https://github.com/yuhang2551/notify-hub/blob/e0ff774/docs/design.md)。

## 一条消息怎么走

```
程序调用 notify-hub send（或 Python 里 notify()）
  │
  ├─ 参数不对（级别不是 urgent 或 normal、链接不是 http/https、来源带空格）→ 报错，退出码 2
  ├─ 配置不对（缺 App ID、渠道写错）→ 报错，退出码 1
  │
  └─ 渲染成 Lark 卡片，发出去
        ├─ 成功 → 退出码 0
        ├─ 连不上、Lark 返回 5xx 或 429 → 隔 2 秒再试，还不行隔 5 秒再试
        │     └─ 三次都不行 → 退出码 1，原因写在错误输出里
        └─ 其他错误（凭证不对、没权限、收件方写错）→ 不重试，退出码 1
```

关键的几个决定：

| 决定 | 为什么 |
|---|---|
| 不存消息，发完就退出 | 发不出去的怎么办，调用方最清楚：邮件监控把它留到下一次汇总，实验脚本也许只记一行日志。notify-hub 再存一份，就又多一套重发的时间表 |
| 发不出去退出码是 1 | 调用方得知道没发出去，才能自己处理。0.2 版这时也返回 0，因为那时它自己会重发 |
| 只当场重试两次（隔 2 秒、5 秒） | 网络抖一下、Lark 偶尔 5xx，几秒后多半就好了；更久的断网交给调用方，不让调用方一直等。代价是：请求其实到了 Lark、只是回复没收到时，重试会多发一张，很少见，多一张总比漏一张好 |
| 只有暂时性的错误才重试 | 凭证不对、没权限、收件方写错，重试多少次都一样，直接报错省时间 |
| 两个级别只决定卡片颜色 | 紧急红、普通蓝。什么时候发由调用方决定，级别不再影响发不发 |
| 不去重 | 同一件事推没推过，调用方自己记得（邮件监控按邮件记在自己的数据库里）。0.2 的 `--key` 还接受，只是不起作用，旧的调用不会报错 |
| Claude Code 的 hook 只试一次 | hook 跑的时候 Claude Code 在等它，不能让它等重试；退出码永远是 0，不会打断 Claude Code |
| 正文纯文本，链接只走按钮 | 邮件内容能影响模型写的摘要；按钮上写着域名，钓鱼链接没法伪装 |
| 卡片正文最多 3000 字 | 中文一个字 3 字节，远低于 Lark 卡片消息 30 KB 的上限；发送时自己按 UTF-8 编码，中文不会被转义得更长 |
| 不常驻、不开端口、没有后台任务 | 被调用时才运行，Mac 上没有东西对外暴露 |
| 命令行为主，Python 接口为辅 | 任何语言、shell 脚本、Claude Code hooks 都能调；邮件监控也通过命令行调用，两个项目各自安装、互不依赖 |

## 两个级别

| 级别 | 卡片 | 例子 |
|---|---|---|
| urgent | 红色，按钮也是红的 | 导师、面试邮件，服务挂了 |
| normal | 蓝色 | 实验跑完，新岗位匹配，邮件汇总 |

## 配置

`~/.notify-hub/.env`，目录和文件都只有自己能读。只有渠道和 Lark 应用机器人的几项（`LARK_APP_ID`、`LARK_APP_SECRET`、`LARK_RECEIVE_ID`），和邮件监控是同一套，`notify-hub init --from ~/.mail-monitor/.env` 直接复制。收件方类型按 id 前缀判断（`oc_` 群、`ou_` 个人），不用另外填。0.2 的配置项留在文件里也没关系，不再读。

## 以后再做

- **双向按钮**：在卡片上点「已处理」「稍后提醒」，结果传回原来的程序。Lark 的长连接模式不需要公网地址，卡片按钮的回调也能从这条连接收到（见 [Hermes Agent 的 Lark 接入说明](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/feishu)），代价是 notify-hub 要一直运行。
- 本机 HTTP 接口、按来源分到不同的群、Lark 以外的渠道。

## 为什么不用现成的

Apprise 这类库能把消息发到几十种服务，ntfy、Bark 要另装 App。这里只要 Lark 应用机器人一种渠道，加上卡片和几次重试，一个几百行的小工具就够了，每一行都看得懂，Lark 凭证也只放在一个地方。
