# 设计说明

**中文** | [English](design_EN.md)

2026-10-27 写的一页设计，按第一段、第二段的实际实现更新过。哪些做了、哪些还没做，以 [更新记录](../CHANGELOG.md) 为准。

## 它解决什么

邮件监控要推到手机，实验跑完要推，定时任务出错要推，Claude Code 等你确认也想推。每个程序各写一遍 Lark 推送，就各有一套重试、去重、免打扰，规则不一致，Lark 凭证也散在好几个地方。

notify-hub 把这一层抽出来：程序只管说"发生了什么、有多急、谁说的"，怎么推、什么时候推、推不推，由它统一决定。

## 一条消息怎么走

```
程序调用 notify-hub send（或 Python 里 notify()）
  │
  ├─ 参数不对（级别写错、链接不是 http/https）→ 报错，退出码 2
  │
  ├─ 去重：同一个 key 24 小时内、同样的内容 10 分钟内来过 → 记一笔 skipped，不发
  ├─ digest 级别 → 存成 digest，等每日汇总
  ├─ 这个来源一小时内已经推了 20 条 → 存成 digest（限流），等每日汇总
  ├─ normal，而且在免打扰时段里 → 存成 held，等时段结束
  │
  └─ 写进发件箱（pending）→ 认领（sending）→ 发 Lark 卡片
        ├─ 成功 → sent；顺手做一次 flush
        └─ 失败 → 回到 pending，1、5、15、30 分钟、之后每小时再试；一天后 failed

notify-hub flush（定时任务每 10 分钟一次，或者任何一次发送成功之后）
  ├─ 免打扰结束了 → 所有 held 合成一张卡片
  ├─ 到了汇总时间、这一次还没发过、不在免打扰时段 → 所有 digest 合成一张汇总卡片
  └─ 到时间的 pending（包括刚合成的卡片）发出去，失败的照上面重试
```

合成卡片是发件箱里新的一条消息（`kind = bundle`），被合进去的消息改成 bundled，记下卡片的 id。发送时再把成员读出来渲染。

关键的几个决定：

| 决定 | 为什么 |
|---|---|
| 先写发件箱再发送（outbox 模式） | 断网、Lark 出错、程序崩了，消息都还在，`flush` 时接着发 |
| 推送失败退出码也是 0 | 调用方（比如邮件监控）不该因为推送失败而中断自己的工作 |
| 发之前先认领 | 两个程序同时补发，也不会把同一条发两次；认领 5 分钟没结果就当那个进程崩了 |
| 连不上 Lark 时停止补发 | 不让每条消息都等一次超时 |
| 去重 key 按来源区分 | 两个程序碰巧用了同一个 key，互不影响 |
| 合成的卡片也是发件箱里的一条消息 | 排队、认领、失败重发都用同一套，不另写；合并在写锁事务里做，两个进程同时 flush 也只合出一张 |
| 汇总看「最近一个汇总时刻之后发过没有」 | 电脑睡过了 18:00，醒来第一次 flush 就补发；同一天不会发两次。第一次用的时候从下一个汇总时刻开始 |
| 时间按本机时区算 | 和你看到的钟一致；测试里固定时区和时钟，夜里跑测试结果也一样 |
| 卡片按 UTF-8 字节数控制大小 | Lark 卡片消息的请求体上限是 30 KB；内容多时少列几条，写上「还有 N 条」 |
| 正文纯文本，链接只走按钮 | 邮件内容能影响模型写的摘要；按钮上写着域名，钓鱼链接没法伪装 |
| 不常驻、不开端口 | 被调用时才运行；补发和汇总交给 launchd 定时跑。Mac 上没有东西对外暴露 |
| 命令行为主，Python 接口为辅 | 任何语言、shell 脚本、定时任务、Claude Code hooks 都能调；邮件监控也通过命令行调用，两个项目各自安装、互不依赖 |

## 三个级别

| 级别 | 什么时候到手机 | 卡片颜色 | 例子 |
|---|---|---|---|
| urgent | 马上，夜里也发 | 红 | 导师、面试邮件，服务挂了 |
| normal | 马上；免打扰时段（默认 23:00–08:00）先存着，结束后合成一张卡发 | 蓝 | 实验跑完，新岗位匹配 |
| digest | 攒起来，每天定点（默认 18:00）按来源合成一张 | 灰 | 订阅、日常统计 |

## 发件箱的状态

| 状态 | 意思 |
|---|---|
| pending | 等着发：新消息，或者失败后等下一次重试 |
| sending | 某个进程正在发 |
| sent | 发出去了 |
| held | 免打扰时段收到的 normal，等时段结束合成一张卡 |
| digest | 等每日汇总（digest 级别，或者被限流） |
| bundled | 已经合进一张卡片（`bundle_id` 是那张卡片） |
| skipped | 重复，没有发 |
| failed | 重试超过一天，放弃了 |

## 配置

`~/.notify-hub/.env`，目录和文件都只有自己能读。Lark 用应用机器人（`LARK_APP_ID`、`LARK_APP_SECRET`、`LARK_RECEIVE_ID`），和邮件监控是同一套，`notify-hub init --from ~/.mail-monitor/.env` 直接复制。收件方类型按 id 前缀判断（`oc_` 群、`ou_` 个人），不用另外填。免打扰时段和汇总时间是 `NOTIFY_HUB_QUIET_HOURS`、`NOTIFY_HUB_DIGEST_TIME`，写 `off` 关掉。

## 以后再做

- **双向按钮**：在卡片上点「已处理」「稍后提醒」，结果传回原来的程序。Lark 的长连接模式不需要公网地址，卡片按钮的回调也能从这条连接收到（见 [Hermes Agent 的 Lark 接入说明](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/feishu)），代价是 notify-hub 要一直运行。
- 本机 HTTP 接口、按来源分到不同的群、临时静音某个来源、Lark 以外的渠道。

## 为什么不用现成的

Apprise 这类库能把消息发到几十种服务，但只管发出去；ntfy、Bark 要另装 App。已经在用 Lark 的话，缺的是级别、去重、限流、重发和汇总这一层。这一层也是常见的工程问题：先落盘再发送（outbox）、幂等去重、限流、退避重试。
